# 🥗 밀스루틴 (MealthRoutine)

20~30대 운동 입문자를 위한 운동·식단 통합 헬스케어 웹 서비스  
2026.11 · 6인 팀 · [팀 저장소](https://github.com/sangsoo-L/MealthRoutine)

`Java 21` `Spring Boot 4` `Spring Data JPA` `MySQL 8` `Docker Compose` `React` `TypeScript`

<br>

## 내 역할

**식단·보상·퀴즈 백엔드**를 맡아 API 19개와 일일 정산 스케줄러를 만들고,  
마지막 주에는 직접 만든 API를 **프론트 화면에 연결**해 코드 리뷰를 받아 반영했습니다.

| 묶음 | API | 내용 |
|---|---|---|
| 음식 | 5 | 음식 검색·상세, 즐겨찾기 목록·등록·해제 |
| 식단 기록 | 5 | 저장·목록·상세·수정·삭제 |
| 식단 목표 | 3 | 생성·조회·수정 |
| 출석·퀴즈 | 3 | 출석, 오늘의 퀴즈 조회·제출 |
| 점수·보상 | 3 | 오늘 점수, 레벨·경험치·포인트, 포인트 내역 |

## 핵심 기능

### 1. 음식 데이터 23,442건 적재
- 식약처 공공데이터 CSV 두 개(음식, 원재료성식품)를 **Python 스크립트로 정리**해 SQL 시드로 만들었습니다.
- `"100g"`처럼 붙어 있는 값은 숫자와 단위로 나누고, 비어 있거나 잘못된 값은 NULL로 처리했습니다.
- 자주 찾는 재료 26개는 검색하기 쉬운 이름으로 바꿨습니다. (`닭고기_가슴(껍질 제거)_삶은것` → `닭가슴살(삶은것)`)
- 도커로 DB를 처음 띄우면 자동으로 들어가서, 팀원 모두 같은 데이터로 개발합니다.

### 2. 식단 기록: 계산은 서버가
- 프론트는 **음식과 몇 인분인지만** 보내고, 섭취량(g)과 영양소는 서버가 계산합니다.
  - 섭취량 = 1인분 중량 × 인분, 영양소 = 100g 기준값 × 섭취량 ÷ 100
  - 1인분은 공공데이터의 식품중량, 없으면 기준량(100g)
- 열량·탄수화물·단백질·지방·당류·나트륨을 항목별, 끼니 합계로 저장합니다.
- 합계를 계속 더하는 값이라 `BigDecimal`로 계산하고 DB `DECIMAL`과 맞췄습니다.
- 수정·삭제 전에 내 기록인지 확인하고, 삭제는 상태만 바꾸는 소프트 삭제입니다.

```http
POST /api/v1/meal-records
{ "mealAt": "2026-11-25T12:30:00", "mealType": "lunch",
  "items": [ { "foodId": 1234, "quantity": 1.5 } ] }

→ items[0]: { "quantity": 1.5, "amountG": 825.00, "caloriesKcal": 412.50 }   // 예시 값
```

### 3. 하루 점수 100점
기획서의 "게임화 요소"를 하루 점수로 구현했습니다. 식단은 **저장한 횟수가 아니라 목표에 얼마나 맞게 먹었는지**로 채점합니다.

| 항목 | 배점 | 기준 |
|---|---|---|
| 칼로리 | 30 | 목표 대비 오차 ±10% 30점 · ±20% 20점 · ±30% 10점 |
| 탄수화물·단백질·지방 | 각 10 | 오차 ±15% 10점 · ±30% 5점 |
| 운동 | 20 | 그날 운동 완료 기록 |
| 출석 | 10 | 그날 출석 |
| 퀴즈 | 10 | 정답 10 · 오답이어도 참여 5 |

### 4. 다음 날 00:05 일괄 정산
- `@Scheduled(cron = "0 5 0 * * *", zone = "Asia/Seoul")`로 매일 0시 5분에 **전날 출석한 사용자**의 점수를 확정합니다.
- 경험치 = 점수, 포인트 = 점수 ÷ 2를 지급하고 레벨을 갱신합니다.
- 한 명이 실패해도 나머지는 계속 처리하도록 사용자별로 예외를 잡았습니다.

### 5. 중복 지급 방지
- 보상마다 `종류:사용자:날짜` 형태의 **지급 키**(예: `DAILY_SCORE:2:2026-11-24`)를 만들어 경험치·포인트 내역에 함께 저장합니다.
- 지급 전에 같은 키가 있으면 주지 않고, 키 컬럼에 **UNIQUE 제약**을 걸어 DB에서도 한 번 더 막습니다.

```java
if (expRepo.existsByExpIdempotencyKey(key)) return;          // 이미 지급한 보상
expRepo.save(ExperienceTransaction.of(userId, xp, type, key)); // exp_idempotency_key UNIQUE
pointRepo.save(PointTransaction.earn(userId, points, type, key));
```

### 6. 오늘의 퀴즈
- 날짜를 1970년부터 지난 일수로 바꿔 **문제 수로 나눈 나머지 번째 문제**를 냅니다. 저장하지 않아도 같은 날은 모두 같은 문제가 나옵니다.
- `(user_id, attempt_date)` UNIQUE로 하루 한 번만 풀 수 있고, 정답·해설은 푼 사람에게만 보여줍니다.

## 설계에서 바꾼 것

**저장할 때마다 포인트 → 하루 점수를 다음 날 한 번만 확정**  
처음 기획은 식단을 저장할 때마다 포인트를 주는 방식이었습니다. 그런데 기록을 지우고 다시 저장하면 포인트를 계속 받을 수 있었습니다.  
그래서 목표에 맞게 먹었는지로 하루 점수를 매기고, 하루가 끝난 뒤 한 번만 보상을 확정하도록 바꿨습니다. 점수는 하루 중에도 조회할 수 있습니다.

## 트러블슈팅

### 같은 날 포인트가 두 번 들어간 문제
- **현상**: 정산을 다시 돌려 보며 DB를 확인하다가, 같은 날 포인트가 두 번 쌓인 것을 발견했습니다.
- **원인**: 지급 키 형식을 바꾸면서 이전 키와 새 키가 서로 다른 값이 되어, "이미 준 보상" 확인을 통과했습니다.
- **해결**: 키를 만드는 곳을 한 군데로 모으고, 경험치·포인트 내역의 키 컬럼에 UNIQUE 제약을 추가했습니다.
- **배운 점**: 기능이 한 번 동작하는 것과, 여러 번 실행해도 결과가 같은 것은 다릅니다.

### 섭취량 단위가 서버와 맞지 않던 문제
- **현상**: 식단 화면을 연결한 뒤 코드 리뷰에서, 섭취량 "적게"를 고르면 일부 음식이 저장에 실패(400)하고 다시 열면 양 구분이 바뀐다는 지적을 받았습니다.
- **원인**: 적게·보통·많이를 고정 그램(50·100·150g)으로 보내고 음식마다 다른 1인분 중량으로 나누다 보니, 최소 0.1인분보다 작아지거나 반올림 오차가 생겼습니다.
- **해결**: 0.5·1·1.5인분을 그대로 보내고, 복원도 인분 기준으로 바꿨습니다. 저장 전 화면 안내도 음식별 1인분 기준으로 맞춰, 보이는 양과 저장되는 양을 일치시켰습니다.
- **검증**: 1인분 1g~5,000g 음식으로 저장 → 재조회 → 변경 없는 수정까지 확인하는 회귀 테스트를 추가했습니다.
- **배운 점**: 프론트와 백엔드 사이의 단위는 서버 계약에 맞춰 보내야 합니다.

## 아쉬운 점과 개선 방향

- **당일 보상이 바로 보이지 않음** → 출석·퀴즈처럼 바로 확정되는 보상은 즉시 지급하고, 식단만 하루 끝에 정산
- **정산 시간에 서버가 꺼져 있으면 그날이 빠짐** → 날짜를 받아 다시 정산하는 기능 (지급 키가 있어 중복 걱정 없음)
- **서버가 여러 대면 스케줄러가 동시에 실행됨** → ShedLock 같은 분산 락으로 한 대에서만 실행
- **문제를 추가하면 퀴즈 출제 순서가 바뀜** → 날짜별 출제 기록 저장
